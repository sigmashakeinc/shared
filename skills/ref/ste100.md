# ASD-STE100 standard for /mono

Source: https://asd-ste100.org/about_STE.html. Issue 9 (January 2025) is the current issue. It has 53 writing rules and about 900 approved words.

## When this applies
Apply it in every /mono run that writes any of these:
- documentation, runbooks, and READMEs
- code comments
- skill text and `ref/` text
- dispatch prompts and worker contracts

## Honest limit
- Apply the writing rules fully (rules 6-14 below).
- Dictionary conformance is approximate. There is no machine check for the approved words.
- This card is a working summary. It is not the licensed standard.
- Report the gaps. Do not claim full conformance.

## Words
1. Use approved, common words. Use one word for one meaning. Use the same word for the same thing each time. Example: use (not utilize), start (not initiate), make sure (not ensure), stop (not terminate), about (not approximately), show (not indicate), get (not obtain), give (not provide), do (not perform), if (not in the event that).
2. Technical names are permitted: identifiers, product names, file names, protocol names, and domain terms (daemon, hook, rule, token, socket, PTY, verdict).
3. Technical verbs are permitted when no approved verb has the same meaning: compile, parse, hash, encode, render, spawn, flush, serialize, cache, log, commit, push.
4. Do not use a phrasal verb when one verb has the same meaning ("configure", not "set up").
5. Do not make a noun cluster of more than three words. Use "of", "for", or a relative clause.

## Sentences
6. Instructions: maximum 20 words for each sentence. Descriptions: maximum 25 words.
7. Write one instruction in each sentence. Use the imperative.
8. Use the active voice. Use the passive voice only in a description when the agent is not known.
9. Do not use "-ing" verb forms, except in technical names.
10. Do not use "would", "could", "should", or "might" for possibility. State the condition, or use "can". Use "must" for a requirement.
11. Do not omit articles, verbs, or subjects. Exceptions: labels, headings, list items that are names, and Go doc comments that start with the identifier.
12. Put the condition first: "If the lock is held, return the error."
13. Write a warning as a command first, then the reason.
14. One topic in each paragraph, maximum six sentences. Use a vertical list for steps and for more than two items.

## Meaning (these rules override all style rules)
15. Keep every fact, condition, limit, number, reason, caveat, and cross-reference.
16. Copy these verbatim: identifiers, code, `backtick spans`, file paths, URLs, numbers and units, rule-ids, quoted strings, error text, CLI commands and flags, env vars, HTTP codes, versions, issue or commit refs, and markers (TODO(x):, FIXME, NOTE:, SAFETY:, INVARIANT:, Deprecated:).
17. Do not change: commented-out code, ASCII diagrams, tables, license headers, example output, regex or format specs, and tool directives (`//go:`, `//nolint`, `@ts-*`, `eslint-*`, `MARK:`, `#pragma`, XML doc tags, JSDoc tags).
18. If a text is already STE, do not change it.

## Checklist enforcement
This is a checklist item in the run. It is not a script.
- Phase 3: write each dispatch instruction in STE. Each implement dispatch tells the engineer to write new or changed comments and docs in STE.
- Phase 4: review the new or changed comments and docs in the diff against this card. Record a one-line verdict.
- A gap that you do not fix is a Reporting item (STE: applied · gaps). Do not hide it.
